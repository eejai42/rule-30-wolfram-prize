# Project: Rule30Research

This is an Effortless Rulebook (ERB) project. All development follows the effortless methodology.

## What this repo is

The Wolfram Rule 30 prize problems, modeled in one rulebook with two halves:

- **The domain model**: Rule 30 itself, built like `effortless-rulebooks/rulebook-examples/simpsons-paradox`.
  Rules, neighborhoods and rule tables; the single seed; a run with its time steps, columns and
  every cell of the light cone to depth 64. Problem 1: every (p, T) periodicity candidate with its
  refuting witness, Theorem C's windows, TX's left-consistency checks, periodic words with computed
  least periods, and B9's tail candidates (the real prefix with a periodic tail spliced on, its own
  left-half lattice, and the one-time check that kills it). Problem 2's prefix densities,
  tolerances and color counts; Problem 3's machine models, algorithms and computations. The
  predicates themselves: each formal statement is a tree of Terms over Operators and Variables,
  written out by the build, with bounded instances whose domain, verdict and witness are computed.
  Right and left diagonals (y_k, w_k) with their dyadic periods, and the facts the diagonal claims
  state. Only structure and inputs are data. Map: `bootstrap/rule30-model/schema.md`.
- **Every claim has a formal statement** (`UnmodeledClaimCount` = 0). The ones not decided by
  instances live in `research/hub/formal_claims.py`; an operator the model does not compute yet
  (the relaxation, window languages, the forcing word q_k, `Reported[...]` table values) has
  `Operators.IsModeled` = 0, and `Predicates.IsComputable` says whether a statement can be decided
  from the model at all. Making an uncomputable statement computable means modeling its operators.
- **The ledger**: assertions, their dependency DAG, evidence files, revisions, and the research
  loops. The ledger reads the model: `Assertions.Predicate` links a claim to its predicate, and
  `EffectiveStatus` (which StatusGroup, IsUsable and CurrentStatus use) is FALSIFIED when the model
  holds a counterexample instance and FINITE_VERIFIED when the model decides a finite statement
  true; otherwise it is the reported status. `Dashboards.ModelContradictionCount` must stay 0, and
  `UnmodeledClaimCount` is how many claims are still only words.

**No prize conjecture is proved here.** See `bootstrap/cmcc_rule30_effortless_migration/research_v05/REPORT.md` for the partial results this ledger started from.

## CRITICAL RULES — Read Before Doing Anything
1. **`effortless-rulebook/effortless-rulebook.json` is the Single Source of Truth.** Everything derived (compiled statuses, the `*.derived-*` files) is regenerated by `effortless build`.
2. **Query the rulebook, never read it whole.** Start with `effortless-rulebook/effortless-rulebook.derived-read-me-1st.txt`, then `*.derived-schema.min.json`. Use python one-liners for data.
3. **Edit the hub with `research/loop_tools.py`**, not by hand. It keeps the Prerequisites closure consistent with Dependencies and keeps Single Line Leaves formatting.
4. **Always build after any change to the rulebook, with `python3 research/build.py`** (or `loop_tools.build()`, or `./start.sh build`), never a bare `effortless build`. The load-bearing fields (PredicateInstances InDomain/Holds/Witness, the Predicates verdicts, Assertions EffectiveStatus and the fields that read it) are cached: their formula is `IF({{IsCached}}=1, {{<Field>Cache}}, <formula>)`, because Postgres recomputes the whole model chain behind them on every read (Assertions took 52 s, Assessments over 90 s). Every `loop_tools.save()` clears the flags, and `build()` compiles with them cleared, fills the caches from that compile and builds again, so a cache always equals its fresh value. A bare `effortless build` after a hand edit would compile with stale caches. To cache another field, add it to `CACHE` in build_model.py. `compile-rulebook` recomputes every calculated, lookup and aggregation field in place; `minimize-rulebook` regenerates the derived ladder.
5. **Never reimplement the status logic** (IsUsable, Blocked, CurrentStatus, ProofEligible, EvidenceGap) in scripts. Read the compiled values.
5a. **The domain model tables are owned by `research/hub/build_model.py`.** It replaces them on every run, so change the model there (not with a one-off edit), then `python3 research/build.py`, then `python3 research/hub/check_model.py`, which compares the built values with the independent oracle in `bootstrap/rule30-model/mock-data/`, and `python3 research/hub/check_postgres.py`, which compares every computed value with the editor's Postgres views (the two substrates have disagreed before: `docs/toolchain-gaps.md` gaps 6 to 13; minimize-rulebook handled 24 MB after the gap 13 fix, and the editor's xlsx step fails above about 11 MB). A claim about Rule 30 belongs in the model as rows and formulas the build decides; Python may only accelerate, and its values enter as `AcceleratorClaims` the model checks.
6. **Ask permission** before changing the assertion statuses of existing claims outside a loop.
7. **A failed compile-rulebook run can look like a no-op.** The CLI does not print a remote tool's error, so check that computed values actually changed (or rerun with `-debug`). Field names that are Python keywords or single letters like `R` make it fail. See `docs/toolchain-gaps.md`.

## The research loop (what "do a loop" means here)

One loop = one hypothesis, tested, recorded, built, consumed.

**Model-native loops (the default from loop 24 on).** When the hypothesis can be stated over the
model, the loop is rows only: `model_tools.add_loop_predicate()` adds the predicate (its statement as
a term tree, `ForAll!` for a binder whose condition bounds its variable), one PredicateInstances row
per deciding model row, and the claim (OPEN, `Predicate` set). `run_loop(..., summarize=...)` builds,
lets `EffectiveStatus` decide, records the decision as a Revision, and finishes. No script computes a
value or a verdict; the loop's rows survive reruns of build_model.py (they carry IntroducedInLoop).
`research/loop-24-kill-bound/run.py` is the pattern. If the hypothesis needs a concept the model lacks,
add it to build_model.py first (a model change, checked by check_model.py and check_postgres.py).

**Computations too large for rows** (millions of windows, onsets in the hundreds) stay Python: the
classic loop below, with the claim's status a report (`IsModelDecided` = 0). Give the claim a formal
statement anyway: add its term tree to `research/hub/formal_claims.py` (CLAIMS), declaring any new
operator in `model_tools.UNMODELED_OPERATORS`, and its `Predicate` link follows. Where the model can
recompute some of the objects (cells, tails, diagonals), load the script's per-object results as
claim rows next to the model's own value, the way `AcceleratorClaims` holds E17's center bits, so
the build checks the script on that sample. Steps 0 to 6 below are the classic loop:

0. The loop is added to Loops as `RUNNING` and built, so the explorer shows it in progress.
1. State the hypothesis as an Assertion (status OPEN) with its Dependencies.
2. Run the experiment or write the proof. Save outputs under `research/loop-NN/` and register each file as Evidence (path + sha256) with EvidenceLinks to the assertions it supports.
3. Record the outcome as a Revision (prior status, new status, reason) and update the assertion's ReportedStatus.
4. Build (`loop_tools.build()`: caches cleared, `effortless build`, caches filled, build again).
5. Consume the compiled Assessments / Dashboards (read, do not recompute).
6. Mark the loop `VERIFIED` with the input hash (rulebook sha256 before the build), the build receipt, and the output hash (rulebook sha256 after the build). Then build again so the Dashboard counts it.
6a. **Update the plan.** Edit `CURRENT` in `research/strategy.py` (headline, approach, what is missing, the next
   target and hypothesis, the honest estimate, and the route's steps with their roles), run it, then
   `effortless build`. The explorer's landing page shows this plan as the most promising path to P1, so a
   loop that changes the picture without updating it leaves the page wrong.

**Grow the DAG from the prize problem down.** Every loop names the open obligation it serves
(B1, B2, B3 or a child of one) and its new claims get a dependency path to that node. Decompose
the open node: state what it would follow from, mark it derived (the build keeps it `BLOCKED`,
and `IsAtRisk` flags the proved-from-open edge), and leave the open child as the next target.
A hypothesis with no path to a prize problem is a side quest and its loop summary must say so;
loops 9 to 12 drifted that way and moved no prize count. Check with the Prerequisites rows of
P1, P2, P3 after the build.

`research/loop_tools.py` `run_loop()` does steps 0 to 6; a loop script supplies only the hub edit. Claims and revisions made inside a loop are tagged with it automatically. A loop that skips the build or the consume step is not VERIFIED.

## Status vocabulary
`DEFINITION`, `PROVED_HUMAN_READABLE`, `REDERIVED_KNOWN`, `FINITE_VERIFIED` are usable premises. Only the first three are proof-eligible. `OPEN`, `FALSIFIED`, `SUPERSEDED` are not usable; any conclusion with such an ancestor compiles to `BLOCKED`.

## Explorer and admin portal
- `./start.sh` launches both. The explorer (progress, loops, claims, dependency graph, proofs) is at http://localhost:7431. The generated admin portal from `effortless-rulebook-editor` is at http://localhost:42442, its API at http://localhost:42441/api/docs.
- **`docs/p1-frontier.md` is the map of the attack on P1**: the chain of open nodes, the proved reductions, and the mechanisms already ruled out. Read it before proposing a loop; update it when a loop changes the chain.
- The explorer's landing page leads with the plan in force (`Strategies`, `StrategySteps`, written by `research/strategy.py`): the route to P1, what blocks it, and where the next loop aims. Each claim page shows the claim's modeled predicate (formal statement, instances, verdict).
- The explorer lives in `explorer/` and reads only the editor API's views. Personas, stories and routes are in `docs/app.md`; read it before changing a screen.
- Any status, count or flag a screen needs is a rulebook field first. Never compute one in the explorer.
- The editor does NOT rebuild by itself when the rulebook file changes from outside; it only offers a rebuild in its UI. `loop_tools.build()` therefore asks it to rebuild after every `effortless build` (skipped when the admin portal has unsaved edits). The editor drops a request that arrives while it is already building (a full rebuild takes about 2 minutes; the data lands in the first few seconds), so a busy editor gets a detached waiter, `research/editor_refresh.py`, that retries until the editor has built the current rulebook. Its log is `.logs/editor-refresh.log`. A plain `effortless build` from the shell does not; click Rebuild in the admin portal or `curl -X POST localhost:42441/api/admin/run-build`.
- The editor's rebuild only adds and updates rows of the tables and fields it already has. A deleted row, a renamed key, a new table or a new field reaches its database only when `./start.sh editor` recreates the container. Research loops never do any of these; `research/hub/build_model.py` does, so recreate the editor after changing the model's schema.

## Commits
- **Commit as soon as a unit of work is finished**: a verified loop, a model change that passes
  check_model.py, a doc update. Do not wait to be asked, and do not leave finished work
  uncommitted between turns. Commit only your own changes: check `git status` and leave files
  another session is still editing for that session's commit.

## Build
- Build: `python3 research/build.py` from project root. It runs `effortless build` (compile-rulebook, minimize-rulebook, effortless-rulebook-editor, rulebook-to-explainer-dag; all remote) twice around filling the caches (rule 4), about 2 minutes.
- No Postgres target is registered. If one is added later, it is a read-only output spoke; the hub does not change.
