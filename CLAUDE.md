# Project: Rule30Research

This is an Effortless Rulebook (ERB) project. All development follows the effortless methodology.

## What this repo is

The Wolfram Rule 30 prize problems, modeled in one rulebook with two halves:

- **The domain model**: Rule 30 itself, built like `effortless-rulebooks/rulebook-examples/simpsons-paradox`.
  Rules, neighborhoods and rule tables; the single seed; a run with its time steps, columns and
  every cell of the light cone to depth 64; Problem 1's period tests and comparisons; Problem 2's
  prefix densities, tolerances and color counts; Problem 3's machine models, algorithms and
  computations; and the predicates themselves (formal statement, quantifiers, variables, bounded
  instances). Only structure and inputs are data; every cell value, witness and verdict is a
  formula. Map: `bootstrap/rule30-model/schema.md` (Shadle artifacts in the same folder).
- **The ledger**: assertions (definitions, theorems, finite verifications, hypotheses), their
  dependency DAG, evidence files with hashes, revisions, and the research loops. `effortless
  build` recomputes every derived status. `Assertions.Predicate` links a claim to the modeled
  predicate it is about, and `PredicateVerdict` shows what the model computes for it.

**No prize conjecture is proved here.** See `bootstrap/cmcc_rule30_effortless_migration/research_v05/REPORT.md` for the partial results this ledger started from.

## CRITICAL RULES — Read Before Doing Anything
1. **`effortless-rulebook/effortless-rulebook.json` is the Single Source of Truth.** Everything derived (compiled statuses, the `*.derived-*` files) is regenerated by `effortless build`.
2. **Query the rulebook, never read it whole.** Start with `effortless-rulebook/effortless-rulebook.derived-read-me-1st.txt`, then `*.derived-schema.min.json`. Use python one-liners for data.
3. **Edit the hub with `research/loop_tools.py`**, not by hand. It keeps the Prerequisites closure consistent with Dependencies and keeps Single Line Leaves formatting.
4. **Always run `effortless build`** after any change to the rulebook. `compile-rulebook` recomputes every calculated, lookup and aggregation field in place; `minimize-rulebook` regenerates the derived ladder.
5. **Never reimplement the status logic** (IsUsable, Blocked, CurrentStatus, ProofEligible, EvidenceGap) in scripts. Read the compiled values.
5a. **The domain model tables are owned by `research/hub/build_model.py`.** It replaces them on every run, so change the model there (not with a one-off edit), then `effortless build`, then `python3 research/hub/check_model.py`, which compares the built values with the independent oracle in `bootstrap/rule30-model/mock-data/`, and `python3 research/hub/check_postgres.py`, which compares every computed value with the editor's Postgres views (the two substrates have disagreed before: `docs/toolchain-gaps.md` gaps 6 to 11). A claim about Rule 30 belongs in the model as rows and formulas the build decides; Python may only accelerate, and its values enter as `AcceleratorClaims` the model checks.
6. **Ask permission** before changing the assertion statuses of existing claims outside a loop.
7. **A failed compile-rulebook run can look like a no-op.** The CLI does not print a remote tool's error, so check that computed values actually changed (or rerun with `-debug`). Field names that are Python keywords or single letters like `R` make it fail. See `docs/toolchain-gaps.md`.

## The research loop (what "do a loop" means here)

One loop = one hypothesis, tested, recorded, built, consumed:

0. The loop is added to Loops as `RUNNING` and built, so the explorer shows it in progress.
1. State the hypothesis as an Assertion (status OPEN) with its Dependencies.
2. Run the experiment or write the proof. Save outputs under `research/loop-NN/` and register each file as Evidence (path + sha256) with EvidenceLinks to the assertions it supports.
3. Record the outcome as a Revision (prior status, new status, reason) and update the assertion's ReportedStatus.
4. `effortless build`.
5. Consume the compiled Assessments / Dashboards (read, do not recompute).
6. Mark the loop `VERIFIED` with the input hash (rulebook sha256 before the build), the build receipt, and the output hash (rulebook sha256 after the build). Then build again so the Dashboard counts it.

**Grow the DAG from the prize problem down.** Every loop names the open obligation it serves
(B1, B2, B3 or a child of one) and its new claims get a dependency path to that node. Decompose
the open node: state what it would follow from, mark it derived (the build keeps it `BLOCKED`,
and `IsAtRisk` flags the proved-from-open edge), and leave the open child as the next target.
A hypothesis with no path to a prize problem is a side quest and its loop summary must say so;
loops 9 to 12 drifted that way and moved no prize count. Check with the Prerequisites rows of
P1, P2, P3 after the build.

`research/loop_tools.py` `run_loop()` does steps 0 to 6; a loop script supplies only the hub edit. Claims and revisions made inside a loop are tagged with it automatically. A loop that skips the build or the consume step is not VERIFIED.

## Status vocabulary
`DEFINITION`, `PROVED_HUMAN_READABLE`, `REDERIVED_KNOWN`, `FINITE_VERIFIED` are usable premises. Only the first three are proof-eligible. `OPEN`, `FALSIFIED`, `SUPERSEDED` are not usable; any conclusion with such an ancestor compiles to `BLOCKED`.

## Explorer and admin portal
- `./start.sh` launches both. The explorer (progress, loops, claims, dependency graph, proofs) is at http://localhost:7431. The generated admin portal from `effortless-rulebook-editor` is at http://localhost:42442, its API at http://localhost:42441/api/docs.
- **`docs/p1-frontier.md` is the map of the attack on P1**: the chain of open nodes, the proved reductions, and the mechanisms already ruled out. Read it before proposing a loop; update it when a loop changes the chain.
- The explorer lives in `explorer/` and reads only the editor API's views. Personas, stories and routes are in `docs/app.md`; read it before changing a screen.
- Any status, count or flag a screen needs is a rulebook field first. Never compute one in the explorer.
- The editor does NOT rebuild by itself when the rulebook file changes from outside; it only offers a rebuild in its UI. `loop_tools.build()` therefore asks it to rebuild after every `effortless build` (skipped when the admin portal has unsaved edits). The editor drops a request that arrives while it is already building (a full rebuild takes about 2 minutes; the data lands in the first few seconds), so a busy editor gets a detached waiter, `research/editor_refresh.py`, that retries until the editor has built the current rulebook. Its log is `.logs/editor-refresh.log`. A plain `effortless build` from the shell does not; click Rebuild in the admin portal or `curl -X POST localhost:42441/api/admin/run-build`.
- The editor's rebuild only adds and updates rows of the tables and fields it already has. A deleted row, a renamed key, a new table or a new field reaches its database only when `./start.sh editor` recreates the container. Research loops never do any of these; `research/hub/build_model.py` does, so recreate the editor after changing the model's schema.

## Build
- Build: `effortless build` from project root (compile-rulebook, minimize-rulebook, effortless-rulebook-editor, rulebook-to-explainer-dag; all remote, a few seconds each).
- No Postgres target is registered. If one is added later, it is a read-only output spoke; the hub does not change.
